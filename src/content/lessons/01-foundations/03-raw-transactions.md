# Сырые транзакции

**Транзакция** — это то, что перемещает ценность в блокчейне. Прежде чем её можно будет транслировать в сеть, она должна быть сериализована в детерминированную строку байтов — это тот самый «сырой транзакционный» (raw tx) шестнадцатеричный код, который вы иногда видите в блок-эксплорерах.

Два факта, которые следует помнить:

1. Формат байтов **специфичен для каждой сети**. Bitcoin и Ethereum используют очень разные кодировки, потому что их модели данных сильно различаются (UTXO против аккаунтов).
2. Формат байтов **детерминирован**. Одна и та же логическая транзакция всегда должна давать одни и те же байты — иначе подписание не сработало бы, так как подпись вычисляется именно по этим байтам.

## Bitcoin — модель UTXO

Транзакция Bitcoin выглядит примерно так:

```
[version: 4 байта]
[input count: varint]
[для каждого входа:
    [prev_txid: 32 байта]
    [prev_vout: 4 байта]
    [script_sig length: varint]
    [script_sig: байты]
    [sequence: 4 байта]
]
[output count: varint]
[для каждого выхода:
    [value: 8 байт (сатоши, little-endian)]
    [script_pubkey length: varint]
    [script_pubkey: байты]
]
[locktime: 4 байта]
```

Это всё. Каждый байт служит своей цели. `txid` вычисляется как `sha256(sha256(serialized_bytes))` — знаменитый «двойной SHA-256» Биткоина.

Транзакции SegWit добавляют раздел свидетелей (witness) после `output count`. Данные свидетелей **не** включаются в `txid` (именно так SegWit исправил проблему пластичности транзакций — свидетелей можно редактировать без изменения `txid`).

## Ethereum — аккаунтная модель

Транзакции Ethereum — это структуры, закодированные с помощью RLP (Recursive Length Prefix — собственный формат сериализации Ethereum). Для современной транзакции EIP-1559 (тип 2):

```
type byte = 0x02
RLP([
  chain_id,
  nonce,
  max_priority_fee_per_gas,
  max_fee_per_gas,
  gas_limit,
  to,                     // 20 байт или пусто для создания контракта
  value,                  // wei, big-endian
  data,                   // данные вызова (call data)
  access_list,            // [[address, [storage_keys...]], ...]
  v, r, s                 // подпись
])
```

Хеш транзакции — `keccak256(0x02 || RLP(...))`.

## Почему «сырые»?

Смысл сырых транзакций в том, что они **переносимы**: вы можете создать их на одной машине, подписать на другой (той, у которой есть доступ к закрытому ключу) и транслировать с третьей. Именно для такого разделения и существует сервис `signing-svc` в нашей лаборатории.

Посмотрите на песочницу справа. Вставьте шестнадцатеричный код транзакции Bitcoin (попробуйте `0100000001...` из любого эксплорера) или Ethereum (`0x02f8...`), и вы увидите структурированные поля, декодированные прямо из потока байтов — с использованием тех же парсеров (`btcd/wire` и `go-ethereum/core/types`), которые платформа использует внутри.

Следующий урок посвящен тому, что на самом деле происходит, когда вы подписываете одну из таких транзакций.

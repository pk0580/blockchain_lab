# Multi-sig 2-of-3: как защитить горячий кошелёк

## Аналогия

Представьте сейф в банке, который открывается только если **два из трёх** ключей одновременно повёрнуты в замках. У кассира, у менеджера филиала и у регионального директора — у каждого по одному ключу. Если кассир захочет ограбить сейф, ему нужно либо договориться с одним из двух коллег, либо физически украсть второй ключ. Один утерянный или украденный ключ ещё не означает потерю содержимого: оставшиеся двое могут открыть сейф и перенести деньги в новый.

Эта схема называется **2-of-3 multi-signature** (далее — «multi-sig 2-of-3»). На блокчейне роль ключей играют приватные ключи, роль сейфа — адрес, с которого нельзя потратить средства без 2 подписей из 3.

## Точное определение

**Multi-sig N-of-M** — схема контроля адресом, при которой:

- адрес «знает» M публичных ключей;
- любая исходящая транзакция считается валидной, только если она содержит **минимум N валидных подписей** разными ключами из этого набора M;
- N и M фиксируются в момент создания адреса и не меняются (адрес — это хеш от описания «N, M, набор pubkeys»).

Для **2-of-3** это значит: три держателя ключей, две подписи нужны и достаточны.

### Bitcoin: native multi-sig через Script

Bitcoin поддерживает multi-sig **на уровне протокола**. В скрипт-языке Bitcoin Script есть опкод `OP_CHECKMULTISIG`, который принимает на стек N подписей и M публичных ключей и проверяет, что среди подписей есть N валидных.

Реальный адрес типа **P2WSH** (Pay-to-Witness-Script-Hash) для 2-of-3 хранит **хеш** от такого скрипта:

```
OP_2  <pubkey1>  <pubkey2>  <pubkey3>  OP_3  OP_CHECKMULTISIG
```

Чтобы потратить средства, инициатор:

1. Собирает unsigned-транзакцию (как обычно).
2. Передаёт её для подписи первому держателю ключа — тот добавляет свою подпись в witness.
3. Передаёт партиально-подписанную транзакцию (PSBT — Partially Signed Bitcoin Transaction, стандарт BIP-174) второму держателю.
4. Второй ключ добавляет вторую подпись.
5. Готовая транзакция broadcast'ится — она содержит 2 подписи и сам скрипт-выкуп.

Третий ключ может вообще ничего не делать. Сеть не знает, какие 2 из 3 ключей подписали — только что подписей достаточно.

### Ethereum: multi-sig как смарт-контракт

Ethereum **не имеет нативного multi-sig** — у обычного EOA-аккаунта ровно один ключ. Чтобы получить multi-sig, заводят **контракт-кошелёк**, который реализует логику «подтверждения N-of-M» внутри себя.

Промышленный стандарт — **Safe** (бывший Gnosis Safe). Архитектурно это контракт, который:

- хранит в storage список owner-адресов и `threshold = N`;
- предоставляет метод `execTransaction(target, value, data, signatures[])`;
- проверяет, что среди подписей в `signatures[]` найдётся `threshold` валидных от разных owner'ов;
- если проверка прошла — делает внутренний вызов `target.call(value, data)`.

Стоимость: подпись 2-of-3 транзакции стоит газ за хранение и за криптографическую проверку нескольких ECDSA-подписей (~50–100k газа сверху vs обычной transfer-tx). Зато Safe умеет много вещей, недоступных native-multi-sig: timelock на операции, role-based access, daily limits, recovery через social graph.

### TRON

TRON поддерживает multi-sig на уровне аккаунта (правда, в более жёсткой формулировке через `permissions` с весами). Концептуально — то же самое: список ключей + threshold, проверка при отправке.

## Зачем это нужно горячему кошельку

Горячий кошелёк биржи постоянно держит ключи в памяти серверов, чтобы быстро отправлять withdrawal'ы. Это **единая точка компрометации**: если злоумышленник вытащил приватный ключ — он опустошает hot wallet за одну транзакцию.

Multi-sig 2-of-3 разделяет ключи между:

- **тёплым подписантом** (online-сервис в нашем дата-центре, доступен в реальном времени);
- **холодным подписантом** (HSM или offline-сервер, требует физического присутствия оператора);
- **резервным ключом** (offline-бэкап в сейфе, доступен только в emergency).

Стандартная ежедневная работа: первые два ключа подписывают withdrawal'ы. Резервный ключ нужен только если кто-то из двух потерян или скомпрометирован — тогда оставшийся ключ + резерв вместе двигают деньги на новый адрес.

При этом **никакой одиночный сервер не может украсть деньги**, даже взломанный root. Атакующему нужно одновременно скомпрометировать минимум 2 разных канала.

## Что в нашей платформе сейчас и что бы поменялось

В нашей лабораторной горячий кошелёк — это **single-key** аккаунт, зарезолвленный через `ConfigHotWalletResolver`. См. конкретные классы:

- `app/Modules/Withdrawal/Application/UseCase/RequestWithdrawal/RequestWithdrawalAction.php` — оркестратор `Fee → Nonce → Build → Sign → Broadcast`.
- `app/Modules/Withdrawal/Infrastructure/TxBuilder/BitcoinTxBuilder.php` / `EvmTxBuilder.php` — формируют unsigned-транзакцию.
- `app/Modules/Network/Domain/Contract/SigningClient.php` (реализация — `HttpSigningClient` → Go signing-svc) — отдаёт **один** подписанный hex.

Чтобы перейти на 2-of-3, потребуется:

1. **TxBuilder возвращает PSBT/SafeTx, а не сразу подписанную транзакцию.** Семантика «один build, одна подпись» больше не работает — нужно несколько шагов подписи.
2. **Появляется state `AwaitingCoSignature` в Withdrawal state machine.** Между `Built` и `Signed` теперь несколько раундов обмена с co-signer'ами.
3. **Минимум два независимых signing-svc**, каждый — со своим ключом и своей политикой допуска (например, HSM-1 разрешает 2FA-подтверждение через telegram-bot, HSM-2 — через одноразовую печать). Платформа их **не знает** — только формирует payload для подписи и получает её обратно.
4. **Orchestration через outbox + webhook**: сначала пишем PSBT в outbox, далее по событию `WithdrawalAwaitingSignature` co-signer узнаёт о новой задаче (опять-таки через webhook на свой endpoint), подписывает у себя локально, шлёт подпись обратно через свой контроллер. Когда подписей достаточно — финализируем и broadcast'им.
5. **Bitcoin**: на стороне нашего TxBuilder в `signing_extras` сохраняем PSBT, в `Domain` появляется VO `PartialSignatures` для трекинга. Стандарт BIP-174 описан в `docs/architecture/decisions/` (нужно завести ADR при реализации).
6. **EVM**: вместо `signRawTx` для EOA — `signSafeTxHash` и сборка в формат Safe. На уровне `EvmTxBuilder` это значит target адрес = Safe-контракт, data = ABI-кодированный `execTransaction`.

## Чего multi-sig **не решает**

- **Скомпрометированную клиентскую логику.** Если злоумышленник внедрил вредонос на сервер orchestrator'а и тот формирует withdrawal на адрес атакующего, оба co-signer'а просто подпишут «легитимный» по их меркам запрос. Multi-sig защищает от утечки ключа, не от подмены бизнес-намерения. Защита от этого — независимая проверка withdrawal'а на стороне каждого co-signer'а (whitelist адресов, дневные лимиты).
- **Внутренний сговор.** 2-of-3 защищает только пока минимум 2 ключа реально хранятся раздельно и держатся разными людьми/системами. Если все три ключа лежат в одной AWS account под одним IAM-role — multi-sig превращается в декорацию.
- **UX простых пользователей.** Pull-based кошелёк физлица с 2-of-3 — это сложно: либо нужен железный второй фактор (Ledger + Trezor), либо social recovery, либо custodian берёт на себя один из ключей и фактически возвращает single-point-of-trust.

## Где это в коде сейчас

- `app/Modules/Withdrawal/Domain/Entity/Withdrawal.php` — state machine, в которую при переезде добавится `AwaitingCoSignature`.
- `app/Modules/Withdrawal/Infrastructure/TxBuilder/` — здесь живёт build-логика, она первой переходит на PSBT/SafeTx.
- `signing-svc/internal/server/` — Go-сервис, который для 2-of-3 нужно будет тиражировать в N независимых экземпляров с разными ключевыми хранилищами.

Следующий урок — про то, **зачем для каждого из этих signing-сервисов нужен HSM**, а не просто файл с приватным ключом на диске.
